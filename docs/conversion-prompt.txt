In the chibicc directory there is a C compiler written in C#. The compiler generates textual assembly for x64 Unix SysV ABI. I would like to change it to generate COFF object files targeting the .NET MSIL bytecode, similar to what MSVC++ `/clr:pure` mode does. We don't need the x64 SysV backend anymore.

The codegen is contained in CodeGen.cs, so I'm expecting this is the file that will be completely rewritten.
We'll also be changing how the driver works: so we will skip compiling textual assembly and composing `ld` command line. Instead of `ld` we'll invoke link.exe (assume link.exe is on PATH, the caller is expected to run vcvarsall first).

I did some research ahead of time, checking how COFF MSIL files are generated by the MSVC++ compiler. The end product should produce outputs similar to MSVC++ compiler. We should be able to link object files generated with MSVC++ with object files generated with chibicc (i.e. ensure we have expected manglings and type names to allow this). The exception will be the `long` and related types: we want to keep the chibicc convention that longs are 8-byte wide, so this is where we'll diverge. We'll also diverge on wide character literals, they'll stay how chibicc has it.

To assist with this task, we have several resources available:

There is a .NET COFF object emitter in tools\coffobjectemitter.cs. It has enough capabilities to generate many patterns, but it might need extending to cover all the patterns that chibicc needs.

I started doing research on object files generated by MSVC++ in `/clr:pure` mode. This research is contained in the `scenarios` directory (read README.md). The MSVC compiler has an undocumented switch to use the C frontend instead of the C++ frontend in `/clr:pure` mode. This switch is `/BC`. Not all C features are supported in this mode, so I had to approximate the shape of the output using C++ (for example, the init.c file is actually compiled as C++, even though it's also valid C, but cl.exe doesn't accept this in `/BC` mode).

It is critical that if the chibicc compiler succeeds (doesn't throw exceptions, exits with 0), the output is valid. If you're not sure how to proceed, we also have an MSVC expert available who is able to answer questions, so ask questions.

The objective is to generate a **complete** backend. Chibicc should be able to compile and link all .c files from the scenarios directory. The only exceptions are .c files that the current chibicc doesn't handle either.

You should also look into handling vararg methods. The test coverage for varargs in the scenarios directory is next to nonexistent, so you'll need to write your own test using the intrinsics chibicc supports.

Chibicc supports variable length arrays - this is another thing MSVC doesn't support, so we don't have it in scenarios - investigate supporting them with alloca IL instructions (write a test case you can validate with! there's a alloca.c file with MSVC-specific intrinsics you might be able to leverage to see codegen).

When generating the `main` method, the compiler should also generate a __CxxPureMSILEntry method so that `main` is callable from our minicrt (see the scenarios directory for samples). One can either pass `/entry:main` to link.exe to force using `main` as-is (this will only possible if `main` doesn't have arguments), or let link.exe use the default entrypoint mainCRTStartup that is defined in minicrt.cc/minicrt.obj.

Chibicc shoud generate an object file, then invoke link.exe with /DEBUG command line option (instead of ld that it's invoking now). After linking, the output EXE and PDB should match the ones produced by MSVC when disassembled (ILDASM) or dumped (CVDUMP), modulo the acceptable differences defined in scenarios/README.md. They should also be executable and produce expected outputs.
